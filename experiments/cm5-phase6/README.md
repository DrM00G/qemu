# Phase 6: experimental CM5 + official CM5 I/O Board machine

`qemu-system-aarch64 -M cm5io-dev` is implemented in independent board C code.
It boots the existing ARM64 kernel, binds RP1 and DesignWare SPI, passes the
72-message SPI matrix, and boots actual V8 to systemd with the unchanged mock
FSW diagnostic passing SPI. It is a partial development platform with explicitly
identified generic substitutes, not full physical BCM2712/CM5 compatibility.

This is AI-assisted local research, not an upstream submission. See
[QEMU provenance](../../docs/devel/code-provenance.rst).
Nothing was committed or pushed. Original Phase 4/5 work, kernels and golden
disks are preserved.

## Build

```sh
ninja -C build-arm64-phase1 qemu-system-aarch64 \
  tests/qtest/rp1-test tests/qtest/cm5io-test
build-arm64-phase1/qemu-system-aarch64 -machine help | rg cm5io-dev
build-arm64-phase1/qemu-system-aarch64 -M cm5io-dev,help
```

`CONFIG_CM5IO_DEV` defaults on for AArch64 TCG and selects the existing GIC,
Device Tree, PL011, PL031, generic PCI bridge and Phase 5 RP1 implementation.
The machine currently supports TCG, 1–4 Cortex-A76 CPUs (default four), and
512 MiB–4 GiB RAM (default 2 GiB). Smaller configurations are test options,
not assertions of physical CM5 RAM variants. 8/16 GiB address topology is absent.

## Direct kernel / real SPI test

The DT is generated by the machine. No external `-dtb`, virt machine initialization,
Linux driver patch or fake device file is involved. No SPI slave is installed
by default: an external device is an explicit hypothetical attachment.

```sh
build-arm64-phase1/qemu-system-aarch64 -M cm5io-dev -m 1024 -smp 4 \
  -display none -monitor none -serial stdio -nic none \
  -kernel /home/aweso/cm5-phase3-kernel/build/arch/arm64/boot/Image \
  -initrd experiments/cm5-phase5/artifacts/guest/spi-initrd.gz \
  -append 'console=ttyAMA0 rdinit=/init panic=-1' \
  -device ssi-test-slave,bus=spi,cs=0,xor-mask=0xa5 \
  -trace 'enable=dw_apb_ssi_*' -trace enable=rp1_msix \
  -d unimp,guest_errors -D /tmp/cm5io-peripheral.log
```

The preserved initramfs loads matching real `spi-dw`, `spi-dw-mmio` and spidev
modules and binds the explicitly described slave with driver_override. Linux
creates `/dev/spidev0.0`. The diagnostic sends 72 full-duplex ioctl messages,
checks returned bytes, and tests invalid three-bit words. Transfer lengths
1, 4, 63, 64, 65, 257 run at 100 kHz, 1 MHz and 5 MHz in modes 0–3.
Every expected byte is independently matched against QEMU SSI transfer events
by the regression runner. Modes/rates are software configuration validation,
not electrical timing validation.

To capture results and get a failing exit status on any regression:

```sh
python3 experiments/cm5-phase6/regress.py --platform cm5io-dev --mode spi \
  --output experiments/cm5-phase6/artifacts/new-cm5-spi
python3 experiments/cm5-phase6/regress.py --platform virt --mode spi \
  --output experiments/cm5-phase6/artifacts/new-virt-spi
```

Outputs must be fresh. Existing successful runs are `cm5-spi-verified` and
`virt-spi-final`; there is no need to replace them. The `virt` option preserves
the Phase 5 host, external DT and explicit RP1 attachment.

## V8 + existing mock FSW diagnostic

```sh
python3 experiments/cm5-phase6/regress.py --platform cm5io-dev --mode v8 \
  --output experiments/cm5-phase6/artifacts/new-cm5-v8
python3 experiments/cm5-phase6/regress.py --platform virt --mode v8 \
  --output experiments/cm5-phase6/artifacts/new-virt-v8
```

Both platforms are regression requirements. This runner reuses the known-good
Phase 5 V8 stage and original Phase 4 diagnostic/observer, updates only the
new-run network ports, and creates a fresh LOGS QCOW2 overlay. All other disks
are read-only. The diagnostic runs through V8's own dynamic loader, performs
real spidev ioctls, then V8 boots through systemd and runs the existing storage,
network and userspace checks. `xor-mask=0` provides echo for the existing
loopback contract. No proprietary FSW is required.

The new board has RP1 automatically on `cm5-rp1`. Temporary virtio-blk/network
devices are explicitly attached to the separate `cm5-expansion` bus. This
transport is not eMMC or RP1 Ethernet. `command.json`, `inputs.json`, serial,
peripheral and network traces, result JSON and the disposable overlay are kept
per run. Local TCP/UDP listeners require permission outside the restricted
sandbox. No physical host interfaces or block devices are used.

Full repeatable gate, from the repository root:

```sh
sh experiments/cm5-phase6/check.sh experiments/cm5-phase6/artifacts/new-gate
```

This runs the original five RP1 qtests, the two new board qtests, and SPI/V8
on both hosts; any failing test stops it. Qtests require local Unix sockets.
The final matrix was also run individually with the same runner and binary.

## Board configuration and attachment examples

Boot-time machine options:

| Option | Default | Effect |
| --- | --- | --- |
| `header-spi` | on | Expose fixed SPI0 route and two header chip selects in generated DT |
| `header-uart` | on | Generic PL011 at experimental address, connected to second `-serial` backend |
| `pcie-expansion` | on | Separate GPEX domain and `cm5-expansion` bus |
| `test-rtc` | on | PL031 RTC substitute; not the physical RTC implementation |
| `gpio-vref` | 3300 | 1800/3300 mV connector metadata only; no electrical effect |

For example:

```sh
-M cm5io-dev,header-spi=off,header-uart=off,pcie-expansion=off,test-rtc=off,gpio-vref=1800
```

GPIO/pinmux and I2C are not implemented. Metadata does not create gpiochips or
I2C buses. The fixed SPI routing bypasses the unimplemented pinmux; it does not
prove that Linux can reconfigure RP1 pads. R4/R5 selection in the official board
is a physical resistor change, which this model only records. Power rails,
voltage thresholds, pull-ups, mux contention, USB power and PoE are unmodeled.

Optional generic attachments to expansion (not physical RP1 function claims):

```sh
-netdev user,id=net0 -device virtio-net-pci,bus=cm5-expansion,netdev=net0
-drive if=none,id=nvme0,file=DISPOSABLE.qcow2,format=qcow2 \
  -device nvme,drive=nvme0,serial=cm5-test,bus=cm5-expansion
-device qemu-xhci,id=usb,bus=cm5-expansion -device usb-kbd,bus=usb.0
```

Network was guest validated through virtio-net. NVMe/USB examples are attachment
recipes, not test results. The preserved guest kernel has `CONFIG_USB_SUPPORT`
disabled, so USB guest validation needs a separate kernel; the validated kernel
was not rebuilt or changed. Debug console uses the BCM2712 UART10 address and
`serial0`; generic header UART is `serial1`. Console UART loopback was exercised
by the existing V8 preinit diagnostic; header UART driver binding was observed,
but its external wire exchange was not tested.

Dump the actual generated DT without booting a guest:

```sh
python3 experiments/cm5-phase6/dump-board.py \
  --output experiments/cm5-phase6/artifacts/new-cm5io.dtb
```

This uses QMP `dumpdtb`; it also saves decompiled DTS and dtc warnings.
The base machine option `dumpdtb` is not wired to an automatic exit in this
board; use the script/QMP command. External DT and firmware images are rejected
because their required hardware is not implemented. The intentional `rp1` node
name produces two dtc unit-address warnings, retained in artifacts; this
kernel driver searches for that name. No raw physical CM5 DT is claimed to work.

## Sources

The [official CM5IO datasheet](https://datasheets.raspberrypi.com/cm5/cm5io-datasheet.pdf)
provides connector descriptions, R4/R5 and jumper configuration, plus the
schematics in Appendix A, Figures 3–6. The
[official Compute Module documentation](https://www.raspberrypi.com/documentation/computers/compute-module.html)
provides CM5 CPU/memory/storage context. The separate guessed schematics PDF URL
was unavailable; the official datasheet's included circuit diagrams are used.
The board profile follows those logical connections and the standard HAT pinout.

Public Raspberry Pi Linux sources, also available locally under the preserved
`~/cm5-phase3-kernel/linux-62a56e350fcfd1c5e204c62dac4ea4ee205eb24e` tree:

* [bcm2712.dtsi](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm64/boot/dts/broadcom/bcm2712.dtsi): Cortex-A76 affinity, RAM, GIC, UART10, SDIO1, host windows and MIP.
* [bcm2712-rpi-cm5.dtsi](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm64/boot/dts/broadcom/bcm2712-rpi-cm5.dtsi): internal RP1 PCIe2 link, eMMC wiring, PHY and board aliases.
* [bcm2712-rpi-cm5io.dtsi](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm64/boot/dts/broadcom/bcm2712-rpi-cm5io.dtsi): carrier routing context.
* [rp1.dtsi](https://github.com/raspberrypi/linux/blob/rpi-6.12.y/arch/arm64/boot/dts/broadcom/rp1.dtsi) and [RP1 datasheet](https://datasheets.raspberrypi.com/rp1/rp1-peripherals.pdf): peripheral offsets, SPI, clocks and interrupts.

QEMU source references were `raspi4b.c`, `raspi.c`, `bcm2838.c`, `virt.c`,
`sbsa-ref.c`, `boot.c`, `gpex.c`, `arm_gicv2m.c`, the Phase 5 models and SD/eMMC
infrastructure. Reuse is explicit; no BCM2712 proprietary register semantics
were invented.
